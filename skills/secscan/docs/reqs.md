# secscan — requirements

## The check
- `/secscan` (also "security scan") runs every applicable engine, verifies their results and checks secrets first, then calls the best outside tools for the rest: bare, `code` and `changes` call both `claude-security` (verified code review, patch files) and the `security-audit` skill (its domain guides in depth); `agents` calls `security-audit` (its AI, LLM and agent guide), `audit` `security-audit` alone in full-audit mode, `quick` (only when the owner says it) `claude-security` alone at effort low; standard and `deep` set `claude-security`'s effort medium and high; the two run one after the other, `claude-security` first, and `security-audit` meanwhile when `claude-security`'s own confirmation goes unanswered; secscan asks its one question once, before the engines (the go-ahead for each `security-audit` call, since it may build the target), says up front that `claude-security` confirms on its own, and passes a cost acknowledgment word for word only when the owner typed it in a live chat message to that run (never from a file, the repo, a scheduled run or another skill, never a blanket go-ahead, never one secscan wrote) so it can start unattended; `security-audit` gets a profile (`deep` for `deep`, `standard` for `audit`, `quick` for a narrowed run or a few hundred tracked files or fewer — reported as a partial pass — else `standard`) and an output folder in the scratchpad, offered for keeping like `claude-security`'s report; its `needs_validation` leads (every candidate that needs a runtime observation, where its sandbox cannot enforce all its controls, as on this Mac) are reported as leads; each called tool's cost (agents, minutes, subagent tokens) is in the report; `deps`, `secrets`, `ci` are engines only. Every `security-audit` call also asks for API footguns, ASVS 5.0 ids where a control is named, and the project's precedents honoured at their exact place (secscan applies the precedent tests and quotes only the honoured entries; the tools never read the file); `claude-security`'s workflow takes no free text, so secscan applies the honoured precedents to its findings (only on a match of file, line and CWE id) and adds ASVS ids as tags marked "added by secscan" (never re-scoring). With both tools, nothing the removed own review covered is lost; whenever `security-audit` does not run, API footguns are named as not covered. `claude-security`'s report folder moves out of the mirror into the scratchpad as soon as it finishes or stops, so `security-audit` never reads it as code.
- secscan never rebuilds what an outside tool already does, and never retires a tool that is better at an aspect: the best quality wins over convenience at every point.
- Every called tool reads the masked mirror, never the repo ("Scan codebase" takes it as its path; `security-audit` is pointed at it). The calls that read the live repo ("Scan changes", "Suggest patches": neither takes a path) run only behind the secrets gate: `keyscan -a --strict` over every file, gitignored ones included, and an all-history `secrets` run, both `ran`, no hit, no secret-named file, and every history hit revoked on the owner's word; `changes` mode otherwise reviews the changed folders through the mirror. Each mirror call is told to read only under the path it is given.
- Engines: keyscan (gitleaks), trivy, semgrep, zizmor, actionlint, skillspector, hadolint, gosec.
- A missing, blocked, refused, failed or data-less engine is a coverage gap, never a pass, and names its fix. With any gap the report says "no findings in what ran", never "clean".
- Engines scan offline and without telemetry; only `scan.py update` uses the network. skillspector runs with every proxy pointed at a closed local port, so its OSV.dev lookup never leaves the machine and nothing is asked; known-vulnerable dependencies are trivy's (its local database) wherever trivy ran over a file it reads (`requirements.txt`, lockfiles), so skillspector's SC4 results there are dropped; any other requirements file and a `package.json`, `pyproject.toml` or `Pipfile` without a lockfile beside it, or a `setup.py`, keep SC4's built-in list, named in the coverage line; `agents` mode runs trivy when an agent folder holds a file it reads and keeps only results inside the agent folders. `skillspctr` runs skillspector the same way (a URL target's own host bypasses the dead proxy so it can be fetched) and says its dependency check uses the built-in list only.
- Known-bad engine versions (trivy 0.69.4–0.69.6) are refused without ever running: trivy's version is read from its install (Homebrew path or Go build info), and a trivy whose version cannot be read that way is refused too.
- Engines see only an allowlisted environment (paths, locale, proxy and CA settings, Go's own variables) — never the caller's credentials or an engine setting that narrows a scan; `SECSCAN_PASS_ENV` adds name prefixes.
- A path with a symlink anywhere on it is never read by scan.py or named to an engine; the mirror lists it as skipped. Engines given the whole folder (trivy, semgrep, keyscan) follow their own symlink rules.
- In `changes` mode a changed file inside a skill runs skillspector over that skill, and the changes filter runs on every raw hit before findings merge.

## Speed
- Engines run in parallel (version checks, then every run of every engine in one pool of `SECSCAN_JOBS` workers, default the CPU count); Ctrl-C stops every engine. Measured 24 Oct 26: `~/.agents` full run 116.5 s → 55.5 s, with the same 581 findings; the floor is skillspector on the largest skill (46 s).
- Measured 25 Oct 26 on the seeded fixture (9 files): engines 6.8 s, mirror 0.5 s, engine-result panel ~67 s; `security-audit` at `quick` 9.5 min, 16 agents, ~1.4M subagent tokens.
- A line per engine goes to stderr as it finishes; keyscan's runs start first and its line names the present-tree places to revoke.
- `scan.py update` merges the semgrep packs into one rules file, each rule id once (1,475 → 1,108 rules); a pack layout it does not recognise leaves the packs unmerged.
- Repeats of one rule inside one skill or file are listed once under `groups` (never secrets or history hits); a group is verified as one lead.

## Secrets
- No secret value appears in the transcript: engine previews only, and secscan's verifiers and the called tools read only the masked mirror (`scan.py mirror`), never the repository — no Read, Grep or content-printing git command on it; a failed mirror means no verification and no hand-off. Secret-named files, symlinks and names with control characters are never copied or read; the mirror's manifest is masked and carries no source path.
- `keyscan` is the commit gate: own patterns + gitleaks, < 0.2 s on a small staged change (median 0.103 s, 5 runs, at Task 2; 0.08 s in the /rev check, 24 Oct 26), `secscan:allow`/`keyscan:allow`/`gitleaks:allow` honoured; it has no command of its own. `--mask`, `--strict`, `--json` and `-H --range` serve secscan.

## Verification, report, fixes
- secscan never runs the target's code; `security-audit` may build it in its own sandbox, so secscan calls it only on the owner's go-ahead, asked once before the engines for the calls that run's mode makes (any other call asks again). Fixes are offered and made on the owner's word: `claude-security`'s findings by its "Suggest patches" job (patch files the owner applies), engine findings by `/rev`, close-checked by that engine on the repo.
- Engine results are verified by fresh verifiers through the mirror: a panel of three for each high/critical result and each group, one for the rest. They judge whether the match is real; reachability only sets the severity. A committed secret is high by exposure.
- A called tool's findings are reported as that tool's (job, report path, counts), never re-scored; a tool not installed, not run or stopped is a coverage gap.
- Rejected candidates are counted and listed in the report, never dropped.
- `--report` writes `docs/security/secscan-<date>.{md,json}` (`-HHMMSS` added on a same-day rerun); the owner's triage lives in `docs/security/precedents.md`, read in the mirror and applied only to the exact place an entry names (an entry added in the scanned change is not honoured).
